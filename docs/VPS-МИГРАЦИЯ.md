# Переезд на VPS + свой Postgres (уход от Supabase)

> Ветка `postgres-vps`. Ветка `main` остаётся на Supabase как рабочий запасной
> вариант — в любой момент можно вернуться `git checkout main`.

## Что заменяем

Supabase давал три вещи, каждую заменяем своим:

| Было (Supabase) | Стало (self-hosted) |
|---|---|
| База данных (Postgres + RLS) | Свой Postgres в Docker; доступ ограничивает код (`user_id` сессии) |
| Вход/пароли (Auth) | Свои таблицы `users` + `sessions`, пароль через scrypt, cookie-сессия |
| Хранилище файлов (Storage) | Файлы на диске сервера (`STORAGE_DIR`), отдаём через защищённый route |
| Письма (сброс пароля) | Свой SMTP (Resend/SendGrid/почта домена) |

**Важно про безопасность.** В Supabase от чужих данных защищал RLS на уровне
базы. Теперь это делает КОД: каждый запрос обязан быть ограничен `user_id`
текущей сессии. Пропустишь один — утечёт чужое. Поэтому миграция идёт через
единый слой запросов и проверки владельца в API-маршрутах.

## Какой нужен VPS

Приложение (Next.js) + Postgres + хранилище файлов на одном сервере.

| Профиль | CPU / RAM / диск | Кому |
|---|---|---|
| **Минимум** | 2 vCPU / 4 GB / 40–80 GB SSD | старт, немного пользователей |
| **Комфорт (рекомендую)** | 2–4 vCPU / 8 GB / 80–160 GB SSD | сборка Next без свопа, запас под файлы |

Почему так:
- **RAM 8 GB.** Сборка Next.js (`next build`) прожорлива; на 4 GB собирать лучше
  со свопом или собирать образ на своей машине. Postgres + Node в работе легко
  живут и на 4 GB, тяжёлый момент — именно сборка.
- **Диск.** Готовые .docx, шаблоны, подписи копятся на диске (`STORAGE_DIR`).
  80 GB — комфортный старт; вынести можно на volume/S3 позже.
- **ОС:** Ubuntu 22.04/24.04 LTS.
- **Регион:** Европа (Gemini заблокирован в РФ/РБ). Провайдера выбираешь сам —
  требования к железу выше.
- **Обязательно:** бэкап базы (`pg_dump` по cron) и диска с файлами.

## Порядок работ (волнами, каждая — отдельный коммит)

- [x] **Волна 0 — фундамент** (сделано): схема `deploy/schema.sql`, клиент БД
      `src/lib/db`, аутентификация `src/lib/auth`, хранилище `src/lib/storage`,
      `docker-compose.yml`, `.env.vps.example`, зависимость `postgres`.
- [ ] **Волна 1 — вход/сессии.** Регистрация по коду, вход, выход, восстановление
      и смена пароля переводятся на новые `users`/`sessions`. Middleware
      (`proxy.ts`) проверяет cookie-сессию вместо Supabase.
- [ ] **Волна 2 — серверные страницы (чтение).** ~30 серверных компонентов
      (`dashboard/**`) переводятся с `supabase.from(...)` на `sql\`...\``.
- [ ] **Волна 3 — мутации из браузера → API-маршруты.** Client-компоненты
      (реквизиты, клиенты, материалы, штампы, чат, мастер) больше не пишут в БД
      напрямую — под каждую операцию появляется API-маршрут с проверкой сессии.
- [ ] **Волна 4 — файлы.** Загрузка/скачивание шаблонов, подписей, печатей,
      готовых .docx переводятся на дисковое хранилище + защищённый route отдачи.
- [ ] **Волна 5 — чистка и деплой.** Удаляем `@supabase/*`, добавляем
      `Dockerfile` + `output: 'standalone'`, инструкцию запуска на VPS (Nginx +
      HTTPS, автозапуск, бэкапы).

После каждой волны приложение собирается и запускается локально против Docker-Postgres.

## Как поднять локально (уже сейчас)

```bash
cp .env.vps.example .env.local     # заполнить пароль Б

docker compose up -d               # поднимет Postgres и применит схему
# приложение заработает против новой базы после Волны 1
```

## Перенос данных из Supabase (когда всё готово)

Экспорт из Supabase (`pg_dump` или выгрузка таблиц) → импорт в свой Postgres.
Пароли из Supabase Auth не переносятся (там другой формат) — пользователям
нужно будет один раз восстановить пароль по почте. Пользователей пока мало,
так что это безболезненно.
