# Переезд на VPS + свой Postgres (уход от Supabase)

> Ветка `postgres-vps`. Ветка `main` остаётся на Supabase как рабочий запасной
> вариант — в любой момент можно вернуться `git checkout main`.

## Что заменяем

Supabase давал три вещи, каждую заменяем своим:

| Было (Supabase) | Стало (self-hosted) |
|---|---|
| База данных (Postgres + RLS) | Свой Postgres в Docker; доступ ограничивает код (`user_id` сессии) |
| Вход/пароли (Auth) | Свои таблицы `users` + `sessions`, пароль через scrypt, cookie-сессия |
| Хранилище файлов (Storage) | Файлы на диске сервера (`STORAGE_DIR`), отдаём через защищённый route |
| Письма (сброс пароля) | Свой SMTP (Resend/SendGrid/почта домена) |

**Важно про безопасность.** В Supabase от чужих данных защищал RLS на уровне
базы. Теперь это делает КОД: каждый запрос обязан быть ограничен `user_id`
текущей сессии. Пропустишь один — утечёт чужое. Поэтому миграция идёт через
единый слой запросов и проверки владельца в API-маршрутах.

## Какой нужен VPS

Приложение (Next.js) + Postgres + хранилище файлов на одном сервере.

| Профиль | CPU / RAM / диск | Кому |
|---|---|---|
| **Минимум** | 2 vCPU / 4 GB / 40–80 GB SSD | старт, немного пользователей |
| **Комфорт (рекомендую)** | 2–4 vCPU / 8 GB / 80–160 GB SSD | сборка Next без свопа, запас под файлы |

Почему так:
- **RAM 8 GB.** Сборка Next.js (`next build`) прожорлива; на 4 GB собирать лучше
  со свопом или собирать образ на своей машине. Postgres + Node в работе легко
  живут и на 4 GB, тяжёлый момент — именно сборка.
- **Диск.** Готовые .docx, шаблоны, подписи копятся на диске (`STORAGE_DIR`).
  80 GB — комфортный старт; вынести можно на volume/S3 позже.
- **ОС:** Ubuntu 22.04/24.04 LTS.
- **Регион:** Европа (Gemini заблокирован в РФ/РБ). Провайдера выбираешь сам —
  требования к железу выше.
- **Обязательно:** бэкап базы (`pg_dump` по cron) и диска с файлами.

## Порядок работ — ВСЁ СДЕЛАНО

- [x] **Волна 0 — фундамент:** схема `deploy/schema.sql`, клиент БД `src/lib/db`,
      аутентификация `src/lib/auth`, хранилище `src/lib/storage`, `postgres`.
- [x] **Волна 1 — вход/сессии:** регистрация по коду, вход, выход, восстановление
      и смена пароля на `users`/`sessions`. Маршруты `src/app/api/auth/*`.
      Middleware проверяет cookie-сессию (`src/lib/auth/proxy.ts`).
- [x] **Волна 2 — серверные страницы (чтение):** все страницы `dashboard/**`
      читают данные через `sql`, ограничивая выборку `user_id` сессии.
- [x] **Волна 3 — мутации из браузера → API-маршруты:** клиенты, реквизиты,
      материалы, штампы, организация, коды, ключ ИИ, статусы дел, чат, автосейв
      блоков — всё через маршруты `src/app/api/*` с проверкой владельца
      (`src/lib/auth/owns.ts`).
- [x] **Волна 4 — файлы:** загрузка/скачивание на диск (`src/lib/storage/local.ts`),
      приватная отдача через `src/app/api/files/[bucket]/[...path]`.
- [x] **Волна 5 — чистка и деплой:** `@supabase/*` удалены, `output: 'standalone'`,
      `Dockerfile`, `docker-compose.prod.yml`.

## Как поднять локально

```bash
cp .env.vps.example .env.local     # заполнить POSTGRES_PASSWORD, DATABASE_URL, GEMINI_API_KEY

docker compose up -d               # поднимет Postgres и применит схему
npm install
npm run dev                        # http://localhost:3000
```

> Локальная сборка `npm run build` на этой машине падает: Turbopack спотыкается о
> кириллицу в пути проекта («Основная/Вайб-кодинг»). Это баг Turbopack, не кода.
> Локально собирать так: `npx next build --webpack`. На сервере путь ASCII —
> обычный `npm run build` работает.

## Деплой на VPS (Docker)

На чистом Ubuntu 22.04/24.04:

```bash
# 1. Установить Docker (если ещё нет)
curl -fsSL https://get.docker.com | sh

# 2. Забрать проект
git clone <repo> doc_creator && cd doc_creator
git checkout postgres-vps

# 3. Настроить окружение
cp .env.vps.example .env
nano .env        # POSTGRES_PASSWORD, GEMINI_API_KEY, APP_URL=https://ваш-домен, SMTP_*

# 4. Собрать и запустить (приложение + Postgres)
docker compose -f docker-compose.prod.yml up -d --build
```

Приложение слушает `127.0.0.1:3000`. Наружу — через Nginx с HTTPS (Let's Encrypt),
проксируя на этот порт. Регистрируетесь по коду приглашения; почта из `ADMIN_EMAIL`
получит права администратора и сможет генерировать коды в Настройках → Приглашения.

**Бэкапы (обязательно):**
```bash
# База — ежедневно по cron:
docker compose -f docker-compose.prod.yml exec -T db pg_dump -U doc doc_creator > backup_$(date +%F).sql
# Файлы — том storage (docker volume) или каталог STORAGE_DIR.
```

## Перенос данных из Supabase (по желанию)

Экспорт таблиц из Supabase → импорт в свой Postgres (структура полей совпадает,
кроме `profiles`→`users`). **Пароли не переносятся** (в Supabase другой формат) —
пользователи один раз задают пароль через «Забыли пароль?» или регистрируются
заново по коду. Пользователей мало — это безболезненно.

## Перенос данных из Supabase (когда всё готово)

Экспорт из Supabase (`pg_dump` или выгрузка таблиц) → импорт в свой Postgres.
Пароли из Supabase Auth не переносятся (там другой формат) — пользователям
нужно будет один раз восстановить пароль по почте. Пользователей пока мало,
так что это безболезненно.
